이 문서는 씬나로가 **누구의 어떤 문제를 왜 풀고, 본선 MVP에서 무엇을 제공할지** 정의한다. 상세 수용 기준은 요구사항 정의서, 타입·알고리즘·스키마는 엔진 및 API 명세에서 관리한다.

문서 간 충돌이 발견되면 조용히 한쪽을 선택하지 않는다. 제출본의 외부 약속을 지키는 범위에서 GitHub의 최신 최종 결정을 우선 확인하고, PRD·요구사항 정의서·엔진 명세를 함께 갱신한다.

## 1. 한 문장 정의

씬나로는 **입출국 항공편과 K-드라마·영화·배우 취향을 바탕으로 검증된 촬영지를 찾고, 실제 열차 시간표와 운영시간 안에서 방문 가능한 지역관광 일정을 생성·편집·재계산하는 여행 의사결정 웹서비스**다.

여행 상품을 예약해 주는 서비스가 아니라, 여행자가 다음 질문에 답하도록 돕는 서비스다.

> “내 비행기 시간과 여행 속도를 고려할 때, 원하는 촬영지를 실제로 몇 곳까지 방문할 수 있는가?”

## 2. 배경과 문제

K-콘텐츠는 방한 동기를 만들지만, 콘텐츠에 대한 관심이 곧바로 실행 가능한 지역 일정이 되지는 않는다. 개별 여행자는 작품·배우·촬영지 관계, 입출국 시각, 열차 시간표, 장소 운영시간을 여러 사이트에서 확인하고 직접 조립해야 한다.

장소 하나를 빼거나 항공편이 지연되면 다음 계산을 다시 해야 한다.

1. 공항에서 출발할 수 있는 시각 계산
2. 지역으로 이동할 열차 선택
3. 촬영지 접근시간과 운영시간 확인
4. 하루 방문 수와 비워 둘 시간 조정
5. 출국편에 늦지 않도록 마지막 일정 역산

기존 추천 서비스가 주로 “어디를 가면 좋은가”를 답한다면, 씬나로는 검증된 후보를 대상으로 **“내 시간 안에 들어오는가”와 “조건을 바꾸면 무엇이 달라지는가”**를 답한다.

## 3. 목표와 비목표

### 3.1 MVP 목표

1. 배우 또는 작품에서 출발해 검증된 촬영지 후보를 찾을 수 있다.
2. 항공편 경계, 열차 시간표, 운영시간과 사용자 여유를 반영한 유효 일정을 생성한다.
3. 사용자가 촬영지·방문일·항공편 시각을 바꾸면 전체 일정을 다시 계산한다.
4. 불가능한 후보를 숨기지 않고 이유와 다음 행동을 보여준다.
5. 네트워크가 끊겨도 대표 데모를 끝까지 실행한다.

### 3.2 MVP 비목표

- 열차·항공·체험의 예약, 결제 또는 잔여좌석 보장
- 입국심사 완료 시각의 자동 예측
- 실시간 택시·버스 경로 및 교통상황 계산
- 모든 배우·작품·촬영지·권역 지원
- 회차·장면 단위 촬영지 정보
- 비공식 배우 방문 장소나 출처가 불명확한 장소 추천
- 회원가입, 계정, 클라우드 일정 저장
- 실시간 LLM을 이용한 사실 판단 또는 경로 계산

## 4. 사용자

### 4.1 우선 사용자

인천공항으로 입국해 특정 K-드라마·영화·배우의 촬영지를 방문하고 싶지만, 한국의 지역 교통과 운영시간을 직접 조합하기 어려운 외국인 개별 여행자다.

### 4.2 핵심 상황

- 여행 전에 좋아하는 배우의 여러 작품 촬영지를 한 일정으로 묶고 싶다.
- 좋아하는 작품의 촬영지를 찾았지만 항공편 사이에 다녀올 수 있는지 모르겠다.
- 모든 장소를 방문할 수 없을 때 무엇을 빼거나 어느 날로 옮겨야 할지 알고 싶다.
- 항공편이 지연됐을 때 첫날 일정이 어떻게 바뀌는지 즉시 확인하고 싶다.

### 4.3 핵심 JTBD

> K-콘텐츠 촬영지 여행을 계획할 때, 검증된 후보와 실제 시간 제약을 한 화면에서 비교하고 조건을 바꿔 보면서, 출국편을 놓치지 않는 실행 가능한 여행의 뼈대를 만들고 싶다.

### 4.4 아직 검증할 가설

- 사용자는 완성 코스보다 변경 가능한 일정의 뼈대를 더 신뢰할 것이다.
- 재계산과 불가능 사유가 반복 검색·수작업 계산 부담을 줄일 것이다.
- 서비스 사용 시점은 출국 전 여행 계획 단계가 가장 유력하다.

지인 여부와 무관하게 외국인 유학생·방한객 커뮤니티·K-콘텐츠 팬 커뮤니티에서 3~5명의 원격 인터뷰 또는 영문 설문을 모집한다. 인터뷰 미완료 상태에서는 사용자 가치 관련 문장을 **검증된 사실이 아닌 가설**로 발표한다.

## 5. 제품 원칙

### 5.1 검증된 관계만 사용한다

- 배우–작품–촬영지 관계는 출처가 확인된 데이터만 표시한다.
- 관계가 없는 장소를 LLM 추론으로 만들지 않는다.
- 장소 상세에 검증 단계와 출처를 표시한다.

### 5.2 계산과 설명을 분리한다

- 사실 판정과 경로 계산은 규칙 기반 엔진이 담당한다.
- LLM은 고도화 단계의 다국어 설명·문장 간소화에만 사용할 수 있다.
- MVP 추천·제외 문구는 사전 작성된 데이터로 제공한다.

### 5.3 모르는 것을 만들지 않는다

- 출처 없는 운영시간과 마감시간을 추정하지 않는다.
- 좌석, 예약 가능성, 물품보관함 실시간 가용성을 보장하지 않는다.
- 현지 접근시간은 실시간 교통 예측이 아닌 보수적 추정치로 표시한다.

### 5.4 사용자가 판단 근거를 볼 수 있어야 한다

- 왜 이 장소가 후보인지 관계와 출처를 표시한다.
- 왜 이 일정이 선택됐는지 비교 기준을 표시할 수 있어야 한다.
- 왜 후보가 제외됐는지 사유와 수정 가능한 조건을 보여준다.

## 6. P0 사용자 여정

### 6.1 공통 시작

1. 입국편 도착 시각과 출국편 출발 시각을 입력하거나 목록에서 선택한다.
2. 항공편 도착 후 공항 출발 시각과 출국일 공항 도착 마감 시각을 확인·수정한다 (#14 절대 시각 입력 — 기본 제안값은 항공편 시각에서 파생: 입국 +120분, 출국 -120분).
3. 배우 또는 작품 검색을 선택한다.

### 6.2 배우 중심 여정

1. 배우를 검색한다.
2. 검증된 출연작을 확인하고 한 개 이상의 작품을 선택한다.
3. 작품별 검증 촬영지를 함께 확인한다.
4. 필수 방문 장소, 여행 속도, 하루 여유를 설정한다.
5. 일정을 생성한다.

### 6.3 작품 중심 여정

1. 작품을 검색한다.
2. 해당 작품의 검증 촬영지를 확인한다.
3. 필요하면 다른 작품을 추가 선택한다.
4. 필수 방문 장소, 여행 속도, 하루 여유를 설정한다.
5. 일정을 생성한다.

### 6.4 편집과 재계산

P0 편집 동작은 다음 세 가지다.

1. 촬영지 제외
2. 방문일 변경 및 고정
3. 입국 또는 출국 항공편 시각 변경

세 동작은 모두 제약을 바꾼 뒤 처음부터 전체 일정을 다시 계산한다. 성공한 경우에만 새 일정을 화면에 반영하며, 실패하면 기존 일정을 유지하고 정확한 이유를 표시한다.

## 8. 일정 생성 제품 정책

### 8.1 하드 제약

다음 조건을 위반한 일정은 결과 후보에서 제거한다.

- 연결 가능한 열차가 존재한다.
- 필수 장소가 포함된다.
- 사용자가 제외한 장소가 포함되지 않는다.
- 사용자가 고정한 방문일을 지킨다.
- 출국 안전 버퍼를 포함해 출국편에 늦지 않는다.
- 검증된 운영시간과 보수적 접근시간 정책을 충족한다.

출국 안전 버퍼의 기본값은 120분이며 하드 제약이다. 하루 안에서 비워 둘 일반 여유도 기본값은 120분이지만 별도 값으로 관리하며, 최소 기준 미달에만 불이익을 주고 초과분에 추가 가점을 주지 않는다.

### 8.2 실행 가능한 일정 간 우선순위

하드 제약을 통과한 일정은 다음 순서로 비교한다.

1. 선택한 배우·작품과의 관련성
2. 방문 가능한 촬영지 수
3. 총 철도 이동시간
4. 환승 횟수
5. 일반 여유 충족 여부

공식 관광정보 등록 정도는 촬영지 후보 목록의 UI 정렬에만 사용하며 일정 엔진 순위와 섞지 않는다. 동일 입력에는 항상 동일한 결과를 반환한다.

### 8.3 운영시간과 지역 내 접근시간

- 역–촬영지 구간은 촬영지별 접근시간 추정값을 사용한다.
- 보수적 버퍼는 **max(20분, 접근시간의 50%)**를 기본 규칙으로 한다.
- 접근시간마다 출처와 검증일을 저장한다.
- 자동 일정에는 다음 장소만 포함한다.
  - 검증된 운영시간 안에 접근시간과 버퍼까지 들어오는 장소
  - 공식 출처로 상시 개방이 확인된 장소
- 운영시간이 미확인인 장소는 자동 일정에서 제외하고 후보 목록에 운영시간 확인 필요로 남긴다.
- 기본 추정으로는 가능하지만 버퍼 적용 시 불가능한 장소는 자동 일정에서 제외하고 방문 가능성 직접 확인 필요로 남긴다.
- 실시간 택시·대중교통 경로는 계산하지 않는다.

화면과 발표에서는 다음 표현을 사용한다.

> 검증된 운영시간과 촬영지별 역 접근시간 추정치에 보수적 버퍼를 적용해, 시스템이 생성한 일정에서는 운영시간 충돌이 발생하지 않도록 합니다. 실제 교통상황에 따라 달라지는 현지 이동시간은 추정치로 명확하게 표시합니다.

## 9. 실패와 예외 경험

### 9.1 자동 제외 사유

- **TRAIN_UNAVAILABLE**: 연결 가능한 열차가 없음
- **DEPARTURE_DEADLINE_EXCEEDED**: 출국 역산 마감 초과
- **ACTIVITY_WINDOW_MISMATCH**: 검증된 활동 가능 시간대와 맞지 않음
- **USER_CONSTRAINT_INFEASIBLE**: 필수 방문 또는 방문일 고정 제약을 만족할 수 없음

USER_CONSTRAINT_INFEASIBLE은 constraintType과 targetId로 실패한 조건과 장소를 구분한다. 사용자가 직접 제외한 장소는 자동 실패 사유 대상이 아니다.

### 9.2 반드시 설계할 화면 상태

- 검색 결과 없음
- 검증 촬영지 없음
- 운영시간 미확인
- 조건을 만족하는 일정 없음
- 재계산 실패 후 기존 일정 유지
- 항공 API 실패 후 스냅샷 전환
- 네트워크 단절

빈 화면이나 일반 오류 문구 대신, 이유와 사용자가 바꿀 수 있는 조건을 함께 보여준다.

## 10. 언어 정책

### P0

- 한국어 핵심 경로 E2E를 완성한다.
- 사용자 노출 문구는 처음부터 ko/en 번역 객체로 분리한다.
- 데모 시드의 배우·작품·장소명은 영문 필드를 필수로 갖는다.

### P1

- P0 E2E 통과 후 핵심 경로 전체 영어 전환에 착수한다.
- 시간이 부족하면 결과 화면 중심의 영문 프로토타입으로 축소한다.
- 완성되지 않은 영어 화면을 전체 다국어 지원이라고 표현하지 않는다.

발표에서는 다음 표현을 사용한다.

> 타깃은 외국인 방한객이며 UI 문구와 콘텐츠의 언어 필드를 분리했습니다. 심사 편의를 위해 한국어로 시연하며, 영어 구현 범위는 실제 완성된 화면까지만 정확하게 표시합니다.

## 11. MVP 범위

### 11.1 P0 — 반드시 실동작

- 반응형 웹
- 입국·출국 시각 입력과 출발 가능시점 선택
- 배우 검색과 작품 검색
- 복수 작품 및 검증 촬영지 탐색
- 필수 방문, 여행 속도, 일반 여유 설정
- 열차 시간표·운영시간·출국 역산을 반영한 일정 생성
- 편집 3동작과 전체 재계산
- 변경 전후 총 이동시간 비교
- 불가능 사유와 기존 일정 유지
- 한국어 E2E 및 ko/en 구조
- 오프라인 스냅샷 실행
- 회귀 프리셋 3개
- 출처·검증일·추정치 라벨

### 11.2 P1 — P0 통과 후

1. 핵심 경로 전체 영어 전환
2. 결과 설명과 제외 사유 가독성 개선
3. 체류시간 조정
4. 항공편 실호출 1건과 5초 내 자동 폴백
5. 진입 환승구간 워크스루 정적 화면
6. Rail&Air 조건·공식 발권 채널 정적 화면

### 11.3 컷 후보

- 짐 보관 정적 화면
- 실시간 LLM 설명
- 추가 배우·작품·촬영지·권역

## 12. 데이터와 데모 범위

### 12.1 고정된 방향

- 대표 배우 방향: 김고은
- 시범 권역 방향: 강원
- 한 명의 배우가 여러 작품과 여러 지역 촬영지로 이어지는 흐름을 보여준다.
- 앱 런타임은 서버 전용 JSON 시드를 읽으며, Python은 오프라인 수집·정제와 회귀 정답 데이터 생성에 사용한다.

### 12.2 팀원 데이터 검증 후 확정할 항목

- 대표 작품 3~4편의 최종 목록
- 촬영지 10~15곳의 최종 목록
- 각 촬영지의 최근접역, 운영시간, 접근시간, 출처, 검증일
- 단일 라이브 데모에서 실제 방문하는 장소

위 항목은 GitHub 이슈 #1의 데이터 검증 결과가 반영될 때까지 **가안**이다. 문서에 특정 목록을 확정값으로 복사하지 않는다.

### 12.3 데모 구성

라이브 데모는 여러 편이 아니라 **하나의 E2E 시나리오**다.

1. 배우 또는 작품 검색
2. 복수 작품·촬영지 확인
3. 여행 조건 설정과 일정 생성
4. 촬영지 제외
5. 방문일 변경
6. 항공편 2시간 지연
7. 재계산 전후와 불가능 사유 확인

회귀 프리셋은 별도 자동 테스트 3개다.

- 경기전 제외
- 항공편 2시간 지연
- 특정 장소 방문일 고정

## 13. 성공 기준

### 13.1 제품·정확도

- 검증되지 않은 배우–작품–촬영지 관계 표시 0건
- 생성 일정의 열차 시간표·출국 역산 하드 제약 위반 0건
- 보수적 운영시간 정책 위반 0건
- 자동 제외된 실행 불가능 후보의 사유 누락 0건
- 추천 근거와 공식 출처 표시

### 13.2 기능·성능

- 배우 시작과 작품 시작 흐름 모두 E2E 통과
- 편집 3동작 모두 전체 재계산 성공 또는 정확한 실패 반환
- 재계산 실패 시 기존 일정 유지
- 시드 규모에서 편집 후 화면 갱신 2초 이내
- 회귀 프리셋 3개 통과

### 13.3 시연 안정성

- 네트워크 차단 상태에서 대표 시나리오 완주
- 초기 상태로 되돌린 뒤 같은 결과 재현
- 라이브 데모 영상과 스냅샷 백업 보유

### 13.4 사용자 가치 검증

다음 중 하나 이상의 증거를 발표 전에 확보한다.

- 촬영지 일정 수작업 계획과 씬나로 사용의 소요시간 비교
- 외국인/K-콘텐츠 팬 3~5명의 인터뷰 또는 영문 설문
- 장소를 바꿨을 때 자동 재계산이 유용한가에 대한 정성 반응

표본이 작으므로 시장 전체를 대표한다고 주장하지 않고, 문제와 흐름을 탐색한 초기 근거로만 사용한다.

## 14. 운영·사업 가설

MVP는 수익모델을 검증하지 않는다. 다음은 심사와 후속 실증에서 확인할 **가설**이다.

1. **B2B2C 연계**: 일정 확정 이후 공식 열차 발권 채널, 지역 관광 플랫폼, 공식 체험 예약처로 수요를 전달한다.
2. **B2G 운영**: 코레일·관광공사·지자체의 외국인 관광 채널에 탑재해 지역 철도 수요와 거점역 이용을 만든다.
3. **비식별 탐색 데이터**: 어떤 콘텐츠 관심이 어느 지역 선택·제외로 이어지는지 집계해 노선·관광상품·정책 설계의 중간 데이터를 만든다.

사용자 동의와 개인정보 최소수집 원칙이 먼저이며, MVP에서는 회원가입과 개인 식별정보를 수집하지 않는다.

## 15. 확장 방향

- 콘텐츠: 더 많은 배우·작품·촬영지, 회차·장면 단위 정보
- 철도망: 강원 시드에서 전국 권역으로 확대
- 데이터: JSON Repository를 DB·외부 API 구현으로 교체
- 이동: 검증 가능한 교통 데이터가 확보될 때 지역 내 경로 고도화
- 언어: 영어 완성 후 추가 언어와 현지화 형식 지원
- 실행 지원: 정적 환승·짐 보관·Rail&Air 안내를 실시간 연계로 발전
- 운영 분석: 비식별 취향–지역 전환 대시보드

## 16. 주요 위험과 대응

| 위험 | 영향 | MVP 대응 |
|---|---|---|

| 운영시간·접근시간 과장 | 불가능 일정 생성 | 미확인 자동 제외, 보수적 버퍼, 추정치 라벨 |
| 외부 API·네트워크 실패 | 데모 중단 | 서버 전용 스냅샷과 자동 폴백 |

| 외국인 타깃과 한국어 데모 불일치 | 심사 질문 | 번역 구조 P0, 실제 영어 완성 범위만 표현 |
| 실시간 AI 부재 질문 | 기술성 오해 | 정확도 정책에 따른 의도적 분리로 설명 |
| 사용자 검증 부족 | 문제 적합성 약화 | 소규모 원격 인터뷰·영문 설문, 한계 명시 |
