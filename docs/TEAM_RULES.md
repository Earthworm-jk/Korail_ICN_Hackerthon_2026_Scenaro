## 브랜치 전략

```
main        ← 데모 가능한 안정 버전 (직접 push 금지, PR로만 승격)
dev         ← 개발 통합 브랜치 (기본 작업 대상)
feature/*   ← 기능 개발 (예: feature/itinerary-engine)
fix/*       ← 버그 수정 (해커톤에서는 hotfix 구분 없이 fix로 통일)
```

- **승격 리듬**: 매일 밤 데모 스모크(김고은 시나리오 E2E) 통과 시 dev → main 승격.
  main은 "어제까지 검증된 안전망"이다.
- PR 머지 후 브랜치는 삭제하되, **삭제 전에 그 브랜치를 base로 하는 열린 PR이 없는지 확인**한다.
  (base 브랜치가 삭제되면 스택된 PR이 통째로 닫힌다.)

## 커밋 메시지 규칙

```
feat:     새로운 기능 추가
fix:      버그 수정
data:     시드 데이터·스냅샷 변경 (이번 프로젝트 추가 타입)
docs:     문서 수정
style:    코드 포맷 변경 (기능 변경 없음)
refactor: 코드 리팩토링
test:     테스트 코드
chore:    빌드 설정, 패키지 수정
```

예시:

```
feat: 코스 재계산 엔진에 변경 전후 이동시간 비교 추가
fix: 출국 역산 마감 계산 오류 수정
data: 강원 촬영지 시드 12곳·역 연결 추가
docs: 요구사항 정의서 v0.2 반영
```

- 커밋 본문(또는 PR 본문)에 관련 요구사항 ID를 적는다. 예: `REQ-EDIT-001`
  → 리뷰를 정의서와 1:1 대조로 할 수 있다(근감소증 방식).

## PR 규칙 (2인 적응판)

- `main` 직접 push 금지, 반드시 PR. `dev` 대상 PR도 리뷰 후 머지가 원칙.
- **속도 조항**: 다음은 상대 리뷰 **필수** —
  코스 엔진(`lib/engine`), 데이터 스키마(Zod), API 명세 변경.
  그 외(화면 스타일·문구·문서)는 **2시간 내 응답이 없으면 셀프 머지 허용**,
  셀프 머지 시 팀 채팅에 한 줄 공지.
- 본선 현장(08-12 - 08-14)에서는 구두 리뷰를 인정하되, PR에 "구두 승인" 코멘트를 남긴다.
- PR 제목 형식 유지: `[feat] 기능명` / `[fix] 버그내용` / `[data] 시드내용`
- 리뷰 코멘트는 확인한 커밋 SHA를 기준으로 남기고, **게시 직전 새 커밋이 없는지 확인**한다.
- `Closes #번호`는 기본 브랜치(main) 머지에만 동작한다.
  **dev로 머지되는 PR은 이슈를 수동으로 닫는다.**
- 충돌 상태인 PR은 CI 체크가 아예 생성되지 않을 수 있다.
  체크가 안 보이면 재시도 전에 mergeable 여부부터 확인.
